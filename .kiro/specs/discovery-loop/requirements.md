# Requirements Document

## Introduction

The AI_Discovery_Loop lets Project Phoenix discover the business rules of the synthetic legacy-sample app by hypothesis and experiment instead of by reading source alone. The AI forms Hypotheses from the Source_Bundle. A deterministic Experiment_Runner tests them against the running Legacy_App. The AI revises the Hypotheses from the Observations. An Independent_Evaluator, running outside the runtime, scores the saved result against the approved Ground_Truth. The MVP target is one complete loop on the legacy-sample app (Kiroween submission).

This spec is rule-agnostic by design. It contains no business-rule values (no thresholds, tiers, or expected outputs) from the Ground_Truth or from the legacy-sample requirements, so the spec itself never carries the answer the AI is supposed to discover. Hypothesis schemas, prompts, and examples derived from this spec must stay equally generic.

Scope boundaries:

- The legacy-sample spec (`.kiro/specs/legacy-sample/`) is read-only context. Its Discovery_Loop (reset, submit scenario, collect response, repeat; no AI) is referenced here as the Deterministic_Discovery_Loop and is not redefined.
- The Phoenix runtime AI is a different actor from the Kiro IDE development agent (see `docs/ai-input-allowlist.md`).
- Only the synthetic legacy-sample is in scope. No unknown code and no real customer data are processed.
- Provenance (Origin), evidence (Evidence), and human approval (Approval) are three separate concepts (Requirement 6). Human approvals of Claim revisions are stored outside every Run directory and cannot be created or changed by any AI (Requirement 23). Existing approvals inside `evaluation/` (Ground_Truth, Migration_Decisions) are out of scope and unchanged.
- The initial implementation scope (MVP) is milestones M0 to M5. M6 and M7 each require a separate explicit human approval, and implementation of M0 to M5 starts only on an explicit human instruction to start implementation (Requirement 21).
- Real AI installation, real AI connection, and any transmission of the synthetic source to a third-party AI service each require separate explicit human approval (Requirement 21).

The Node.js runtime is container-based and is not installed on the host (RESOLVED by A2: host installation is excluded).
5. OPEN: Kiro CLI is not installed locally. Its documented behavior (tool-call events, MCP configuration, knowledge features, headless mode) is locally unverified until M6.
6. OPEN: `.gitignore` does not yet list `discovery/runs/`. It must be extended during implementation (Requirement 12). Whether `discovery/approvals/` is tracked by Git is decided at the design stage.

8. OPEN: The Rule_Expression_Language must be defined in the design without operators or names that hint at a specific business rule.
9. RESOLVED (A6, A7): Ground_Truth boundary cases executed with a temporary fixture product, units needing non-JSON bodies, and units needing a specific lexical number form are reported `uncovered` with reason codes and listed as evaluation limitations (Requirement 14.13 and 14.14).

11. OPEN: The form of the AI_Sandbox controller (host-side controller or alternative) is decided and verified in M6.
12. RESOLVED (A1): The discovery-loop is an independent new spec.
13. RESOLVED (A2): Language and runtime are fixed as TypeScript on container-based Node.js; only version pinning remains open (item 4).

15. RESOLVED: The cross-runner lock is a mechanical, Run-level lock that reuses the existing Windows named mutex `Local\ProjectPhoenixGroundTruthEvaluation`, so the conformance runner needs no change (Requirement 24). Until it is implemented, concurrent execution is prohibited by procedure.

## Glossary

- **Legacy_App**: The synthetic PHP 5.6 / MySQL 5.7 order-management application defined in the legacy-sample spec, running in the isolated legacy Docker environment.
- **Test_API**: The HTTP interface of the Legacy_App as defined in the legacy-sample spec.
- **Ground_Truth**: The approved expected specification in `evaluation/ground-truth/ground-truth.json`, as defined in the legacy-sample spec.
- **Migration_Decisions**: The human decision registry `evaluation/migration-decisions.json`, as defined in the legacy-sample spec.
- **Conformance_Baseline**: The generated file `evaluation/results/ground-truth-conformance.json`, which records observed legacy behavior per Ground_Truth scenario unit.
- **Deterministic_Discovery_Loop**: The legacy-sample term `Discovery_Loop`: an automated cycle that resets the Legacy_App, submits a scenario, collects the response, and repeats, without AI. Referenced, not redefined.
- **AI_Discovery_Loop**: The loop defined by this spec: Hypothesis generation, Experiment, Observation, and Hypothesis update. It uses the reset and execute capability of the Deterministic_Discovery_Loop only through the Experiment_Runner.
- **Loop_Orchestrator**: The module (proposed `packages/discovery-loop`) that sequences the AI_Discovery_Loop. It holds no Ground_Truth access.
- **Run**: One execution of the AI_Discovery_Loop from start to termination, identified by a unique run identifier.
- **Iteration**: One cycle within a Run consisting of Hypothesis generation or update, Experiment generation, policy validation, execution, and comparison.
- **Run_Manifest**: The file among the Run records that lists every Run artifact with its content hash, plus the configuration, limits, provider identity, and tool versions of the Run.
- **Source_Bundle**: The set of files read from the 7-file allowlist in `docs/ai-input-allowlist.json`, together with their content hashes.
- **Source_Bundler**: The module that builds the Source_Bundle.
- **Citation_Verifier**: The deterministic module that checks Citations against the Source_Bundle.
- **Comparator**: The deterministic module that compares a Prediction with an Observation.
- **Kiro development agent**: The Kiro IDE agent that builds this repository; it is not the Phoenix runtime AI.
- **Payload_Audit**: The deterministic check performed on the exact payload before every transmission to an AI_Provider.
- **Payload_Auditor**: The module that performs the Payload_Audit.
- **AI_Provider**: An implementation of the provider abstraction in `packages/ai-client` that accepts a structured request and returns a structured response.
- **Mock_Provider**: An AI_Provider that returns deterministic canned responses and needs no external dependency.
- **Kiro_CLI_Provider**: An AI_Provider that invokes Kiro CLI inside the AI_Sandbox. It is the first candidate real provider.
- **AI_Sandbox**: The dedicated isolated container in which the Kiro_CLI_Provider runs.
- **Hypothesis**: A structured, versioned set of Claims about the behavior of the Legacy_App, with a unique identifier.
- **Claim**: One statement within a Hypothesis. A Claim has a condition and an effect, each given as description text and as a Rule_Expression_Language expression, an optional threshold description, a confidence, open questions, and Citations, and it has a unique identifier that stays the same across revisions. Each stored version of a Claim is a Claim revision with its own revision identifier. The Origin, Evidence, and Approval of a Claim revision are held in separate records and are not fields of the Claim content.
- **Citation**: A reference of the form file, line range, and quoted text, pointing into the Source_Bundle.
- **Experiment**: A structured proposal, with a unique identifier, that states the Claim or Hypothesis it tests, a request sequence, optional declarative preparation steps, and a Prediction.
- **Prediction**: The response status and response fields the AI expects for an Experiment.
- **Observation**: The response status, body, and relevant state-check responses that the Experiment_Runner recorded for an Experiment.
- **Evidence**: An append-only record with a unique identifier and an Evidence_Kind that links a Claim revision to a Citation verification result (kind `source`) or to an Experiment, a Prediction, an Observation, and a comparison result (kind `experiment`). Evidence is separate from Origin and from Approval.
- **Evidence_Kind**: One of two independent kinds of Evidence: `source` (Citation verification; the Source_Bundle contains the cited text) and `experiment` (Observations compared to Predictions; observed Legacy_App behavior). Neither kind implies business-specification correctness.
- **Experiment_Runner**: The deterministic module that executes accepted Experiments against the Legacy_App via allowlisted Test_API operations and manages resets and state preparation.
- **Experiment_Policy**: The deterministic rule set that validates each Experiment before execution.
- **Evidence_Store**: The append-only, hash-chained storage of Run records. During a Run the records are in the Run_Volume; after a verified export they are under `discovery/runs/<run-id>/`.
- **Run_Volume**: The Linux-side Docker named volume dedicated to one Run, to which the runtime writes the Run records during the Run (Requirement 12.17).
- **Incoming_Export**: The temporary export location `discovery/runs/.incoming/<run-id>/` to which the Launcher copies the Run records from the Run_Volume after the Run (Requirement 12.18).
- **Completion_Marker**: The file written last by the Launcher into a verified export, containing the SHA-256 hash of the Run_Manifest. A Run without a Completion_Marker is not complete (Requirement 12.20).
- **Reason_File**: The file the Launcher writes into an export that is `incomplete` or `interrupted`, stating the failing step or the reason (Requirement 12.21).
- **Discovery_Lab_Network**: The internal Docker network with the fixed name `phoenix-discovery-lab`, referred to in this document as `discovery-lab`.
- **Independent_Evaluator**: The separate-process evaluator, located outside the runtime modules, that scores a saved Run against the Ground_Truth and Migration_Decisions.
- **Approved_Divergence**: One of the 6 approved incompatibilities recorded in `evaluation/migration-decisions.json`, where the observed legacy behavior differs from the approved target specification.
- **Legacy_Behavior_Restoration**: Evaluation axis A: how accurately the Hypotheses reproduce the actual observed legacy behavior.
- **Target_Specification_Alignment**: Evaluation axis B: how closely the Hypotheses agree with the approved Ground_Truth and Migration_Decisions.
- **Origin**: The provenance of the content of a Claim revision, that is, who produced it: `ai-inferred` (produced by the AI_Provider) or `human-authored` (written by a human; not produced by the loop). The loop produces only `ai-inferred`. The Origin of a Claim revision never changes (Requirement 6).
- **Rule_Expression_Language**: The generic, total, side-effect-free expression language defined in the design, in which Claim conditions and expected responses are written (Requirement 4.6).
- **Evidence_Status**: The aggregate status (`absent`, `supported`, `contradicted`, `mixed`) of one Evidence_Kind for one Claim revision, derived only from the Evidence records of that kind (Requirement 6).
- **Approval**: A human decision on a target (a Claim revision, a Run, or a Gate), expressed as an Approval_Record. Approval is separate from Origin and from Evidence (Requirements 6 and 23).
- **Approval_Record**: An append-only record in the Approval_Store with the approver identity, a timestamp in ISO 8601 with offset, the target (Claim revision identifier together with its Run identifier, Run identifier, or Gate identifier), the decision (`approved`, `rejected`, or `needs_changes`), the rationale, `recorded_by`, and, for a correction or withdrawal, the `supersedes` field (Requirement 23).
- **Approval_Store**: The append-only, hash-chained storage of Approval_Records outside every Run directory (for example `discovery/approvals/`), to which the runtime container has no write access (Requirement 23).
- **Launcher**: The host-side command that acquires the Run_Lock, creates the Run_Volume, issues the Run_Lease, starts the runtime container with `docker run`, and, after the Run, exports and verifies the Run records (Requirements 12 and 24).
- **Run_Lock**: The lock held by the Launcher for the whole Run: the Windows named mutex `Local\ProjectPhoenixGroundTruthEvaluation` plus an exclusive lock among AI_Discovery_Loop Runs (Requirement 24).
- **Run_Lease**: The Launcher-issued token, bound to one Run identifier and to the Launcher process, without which the runtime refuses to start a Run and whose invalidity makes the runtime stop the Run (Requirement 24).
- **Discovery_Override**: The separate Compose override file (for example `infra/docker-compose.discovery.yml`) that defines only the `discovery-lab` network and the membership of `reverse-proxy` in it. It defines no `discovery-runtime` service (Requirement 18).
- **Version_Pinning_Record**: The repository record of exact verified versions required by Requirement 20.6.
- **Gate**: A point in the phased delivery at which work stops until a human gives explicit approval.

## Requirements

### Requirement 1: Source_Bundle Construction from the Allowlist

**User Story:** As a Phoenix engineer, I want the AI input built only from the explicit allowlist, so that nothing outside the approved source files can reach the AI.

#### Acceptance Criteria

1. WHEN the Source_Bundler is started, THE Source_Bundler SHALL read the allowlist from `docs/ai-input-allowlist.json` and SHALL read exactly the files listed there as concrete relative paths, in the listed order, resolved against the repository root.
2. THE Source_Bundler SHALL NOT enumerate directories, expand wildcards, or read any file that is not listed.
3. IF a listed path is absolute, contains a traversal segment (`..`), resolves to a directory, resolves through a symbolic link, junction, or hard link, is a duplicate of another listed path (compared after path normalization), is missing, or is unreadable, THEN THE Source_Bundler SHALL stop with an error that identifies the offending path and the reason, SHALL produce no Source_Bundle, and SHALL write no manifest.
4. IF the allowlist JSON is missing, is not valid JSON, has no `files` list, has an empty `files` list, or lists an entry that is not a string, THEN THE Source_Bundler SHALL stop with an error, SHALL produce no Source_Bundle, and SHALL write no manifest.
5. WHEN the allowlist JSON and the table in `docs/ai-input-allowlist.md` list a different set of files or a different order, THE Source_Bundler SHALL stop with an error that names the first differing entry, SHALL produce no Source_Bundle, and SHALL write no manifest.
6. WHEN all allowlist checks pass, THE Source_Bundler SHALL write a manifest that lists, in allowlist order, each file path and the lowercase hexadecimal SHA-256 hash of its content, with each CRLF and each lone CR line ending normalized to LF before hashing and with no other byte change.
7. WHEN the Source_Bundler writes the manifest, THE Source_Bundler SHALL verify that the manifest paths equal the allowlist paths exactly, in the same order, with no extra entry and no missing entry, and SHALL stop with an error and produce no Source_Bundle if they differ.
8. FOR ALL identical file contents and an identical allowlist, THE Source_Bundler SHALL produce a byte-identical manifest and byte-identical Source_Bundle content, with no wall-clock value, random value, or host-specific path in either (determinism).
9. THE Source_Bundler SHALL be implemented without any import of, or file access to, `evaluation/`, `tests/`, `.kiro/`, `infra/`, or any `README.md`, and THE test suite SHALL verify this by static dependency analysis and by an attempted-read check of those locations.

### Requirement 2: Payload_Audit Before Every Send

**User Story:** As a Phoenix engineer, I want every outbound AI payload audited, so that leakage of the Ground_Truth or of non-allowlisted content is blocked before transmission.

#### Acceptance Criteria

1. WHEN the Loop_Orchestrator prepares a call to an AI_Provider, THE Payload_Auditor SHALL complete a Payload_Audit on the exact byte sequence that will be transmitted, and THE Loop_Orchestrator SHALL NOT start the call until the Payload_Audit has returned a pass result.
2. WHEN the Payload_Auditor audits a payload, THE Payload_Auditor SHALL save the exact audited bytes and their SHA-256 hash in the Evidence_Store together with the audit result (`pass` or `blocked`), the list of checks performed, and the outcome of each check.
3. WHEN the Payload_Auditor returns a pass result, THE Loop_Orchestrator SHALL transmit a byte sequence whose SHA-256 hash equals the hash saved in the Evidence_Store, and SHALL record the request hash of Requirement 3.7 equal to that hash; IF the hash of the bytes about to be transmitted differs from the hash of the audited bytes, THEN THE Loop_Orchestrator SHALL NOT make the call and SHALL record the failure.
4. IF the payload contains the Ground_Truth canary or any decoy canary, THEN THE Payload_Auditor SHALL block the call, record the failure with the identifier of the matched canary (not the canary value), and make no AI_Provider call for that payload.
5. IF the payload contains a file path that is not an exact path listed in `docs/ai-input-allowlist.json`, THEN THE Payload_Auditor SHALL block the call and record the failure with the offending path.
6. IF the Source_Bundle content in the payload differs from the Source_Bundle manifest hashes (any file altered, added, missing, or reordered), THEN THE Payload_Auditor SHALL block the call and record the failure with the affected file path.
7. THE Payload_Auditor SHALL check that every part of every payload is one of the following, and SHALL block the call and record the failure if any part is not: Source_Bundle content verified against the manifest, a stored Hypothesis revision, a stored Experiment, Observation, or comparison result of the same Run, or fixed instruction text of the Loop_Orchestrator.
8. IF the payload contains Ground_Truth content, Migration_Decisions content, Conformance_Baseline content, review package content, or evaluation results, THEN THE Payload_Auditor SHALL block the call and record the failure. THE Payload_Auditor SHALL detect such content using a configured list of fingerprints supplied outside the Loop_Orchestrator module, including at least one fingerprint per restricted file under `evaluation/`, and not by canary or path matching alone.
9. IF any Payload_Audit check cannot be completed, or the audit configuration (canaries, decoys, fingerprints, allowlist) is missing, unreadable, or empty, THEN THE Payload_Auditor SHALL block the call, record the failure with the reason, and treat the result as `blocked`.
10. IF a Payload_Audit returns `blocked`, THEN THE Loop_Orchestrator SHALL NOT retry the same payload, SHALL NOT count the blocked call against the AI_Provider retry limit of Requirement 11, and SHALL stop the Run with termination reason `payload_audit_blocked` and write the Run_Manifest.
11. THE Payload_Auditor SHALL treat canary, fingerprint, and path checks as necessary and not sufficient evidence of isolation; THE Run_Manifest SHALL additionally record, in separate fields, the verification status of the runtime access rights (Requirement 15) and of the AI execution environment (Requirement 16), and a `pass` result SHALL NOT be recorded as evidence that either environment is isolated.
12. THE Payload_Auditor SHALL obtain the canary, decoy, and fingerprint values from a configuration supplied outside the Loop_Orchestrator module, so that the Loop_Orchestrator can audit payloads without reading `evaluation/ground-truth/ground-truth.json`, and SHALL NOT write a canary, decoy, or fingerprint value into any log, Run artifact, or Run_Manifest, referencing matches by identifier only.
13. THE test suite SHALL verify, for each of criteria 3 to 9, that a payload built to violate exactly that check is blocked, and that a payload that violates none of them passes.
14. THE Payload_Audit (verification of the content that is sent) and the execution-environment access control (verification of what the runtime process can read, Requirement 15) SHALL be separate checks with separate tests, and THE Run_Manifest SHALL record their results in separate fields (`payload_audit` and `ground_truth_access_denial`).
15. THE Loop_Orchestrator SHALL NOT use a passing Payload_Audit as evidence for the execution-environment access control, and SHALL NOT use a passing access-denial verification as evidence for the Payload_Audit.
16. THE Loop_Orchestrator SHALL start a Run only WHEN both the Payload_Audit configuration check of criterion 9 and the Ground_Truth access-denial verification of Requirement 15.14 have passed in that Run.

### Requirement 3: AI_Provider Abstraction and Mock_Provider

**User Story:** As a Phoenix engineer, I want a provider abstraction with a deterministic Mock_Provider, so that the full loop runs offline and the real provider can be swapped in by configuration.

#### Acceptance Criteria

1. THE AI_Provider interface SHALL accept a structured request and return a structured response, and THE Loop_Orchestrator SHALL select the AI_Provider implementation by a single configuration value, so that changing that value between the Mock_Provider and the Kiro_CLI_Provider requires zero changes to caller source files.
2. THE Mock_Provider SHALL pass its own test suite, including one complete Run, before implementation of any real AI_Provider begins.
3. WHEN the Mock_Provider receives two requests whose bytes are identical, THE Mock_Provider SHALL return byte-identical responses, independent of wall-clock time, random values, call count, and earlier calls.
4. WHERE the Mock_Provider is configured, THE Loop_Orchestrator SHALL execute a complete Run to a recorded termination reason with no network access other than the Experiment_Runner's access to the Test_API, and with no external AI service.
5. THE Mock_Provider SHALL return responses that pass the same JSON schema validation (Requirements 4 and 7) as responses from the Kiro_CLI_Provider.
6. THE AI_Provider interface SHALL expose no file-system, process, network, Docker, or Git operation to the AI, and THE Mock_Provider SHALL perform none of these operations while serving a request.
7. WHEN an AI_Provider call completes, THE Loop_Orchestrator SHALL record in the Evidence_Store the provider identity, provider version, model identifier (or the value `not_applicable` when the provider has no model), request hash, and response hash, and SHALL record the same provider identity in the Run_Manifest.
8. IF an AI_Provider call returns an error, returns a response that cannot be parsed, or exceeds the per-call time limit of Requirement 11, THEN THE Loop_Orchestrator SHALL discard the response, record the failure with a reason of `error`, `unparseable`, or `timeout`, and retry the call up to the retry limit of Requirement 11, with each retry subject to a new Payload_Audit.
9. IF the retry limit is exhausted for an AI_Provider call, THEN THE Loop_Orchestrator SHALL stop the Run with termination reason `provider_failure` (Requirement 11).
10. THE Mock_Provider canned responses SHALL be written by hand as static fixtures, and THE Mock_Provider SHALL NOT generate, copy, derive, or compute them from the Ground_Truth, Migration_Decisions, Conformance_Baseline, evaluation results, or any observed Legacy_App behavior.
11. THE Mock_Provider canned responses SHALL contain no Ground_Truth canary or decoy canary, and THE Mock_Provider module SHALL have no import of, and no file access to, `evaluation/`.
12. IF the Mock_Provider receives a request for which no canned response exists, THEN THE Mock_Provider SHALL return an error response that identifies the request as unmatched and SHALL NOT fabricate a response.
13. THE Mock_Provider canned responses SHALL include at least one response for each of three request kinds (Hypothesis generation, Experiment generation, and Hypothesis revision), so that a Run can complete at least 1 Iteration with at least 1 accepted Experiment.
14. THE Mock_Provider canned responses SHALL NOT be required to describe the actual behavior of the Legacy_App correctly, and THE Independent_Evaluator results for a Run whose recorded provider identity is the Mock_Provider SHALL NOT be presented as evidence of AI discovery capability.

### Requirement 4: Hypothesis Generation

**User Story:** As a Phoenix engineer, I want the AI to propose structured Hypotheses from the Source_Bundle, so that the proposals can be validated, tested, and evaluated mechanically.

#### Acceptance Criteria

1. WHEN a Run starts and the Payload_Audit of the request has passed, THE Loop_Orchestrator SHALL send the Source_Bundle to the AI_Provider and request one Hypothesis.
2. THE Loop_Orchestrator SHALL validate each Hypothesis against a JSON schema before storing or using it.
3. THE Hypothesis schema SHALL require each Hypothesis to contain 1 to the configured Claim limit of Requirement 17.2 (default 50) Claims and SHALL reject any field that the schema does not define.
4. THE Hypothesis schema SHALL require each Claim to contain all of the following, and SHALL define no other Claim content:
   - a condition, given both as a description (non-empty text, at most 1,000 characters) and as a machine-evaluable expression in the Rule_Expression_Language;
   - an effect, given both as a description (non-empty text, at most 1,000 characters) and as a machine-evaluable expected response (response status and response field values, where each value is a literal or a Rule_Expression_Language expression);
   - at least one Citation, as defined in Requirement 5;
   - a confidence, with exactly one of the values `low`, `medium`, or `high`;
   - a list of open questions, with 0 to 20 items, each non-empty text of at most 500 characters. An open question is a point the AI could not confirm from the Source_Bundle.
5. THE Hypothesis schema SHALL allow a Hypothesis to declare named derived values and lookup tables that its Claim expressions reference, and SHALL allow each Claim an optional threshold description (non-empty text, at most 200 characters). WHEN the AI supplies no threshold, THE Loop_Orchestrator SHALL store the Claim with the threshold absent and not with an empty or null value.
6. THE Rule_Expression_Language SHALL be generic, total, and side-effect free: it SHALL consist only of literals, references to request inputs, references to named derived values and lookup tables declared in the same Hypothesis, integer arithmetic, comparison, and boolean operators; it SHALL contain no loop, recursion, function definition, I/O, or reference outside the Hypothesis and the request inputs; and evaluating an expression on the same inputs SHALL always return the same result or a defined evaluation error.
7. THE Hypothesis schema, the Rule_Expression_Language, the Hypothesis request template, and any example in them SHALL contain no field name, enumeration value, operator name, or example text that names or hints at a specific business rule of the Legacy_App.
8. IF a Hypothesis fails schema validation or contains an expression that does not parse in the Rule_Expression_Language, THEN THE Loop_Orchestrator SHALL reject the whole Hypothesis, record the validation errors in the Evidence_Store, and not use any part of the rejected Hypothesis.
9. IF every Hypothesis request of a Run fails validation up to the retry limit of Requirement 11, THEN THE Loop_Orchestrator SHALL stop the Run with termination reason `provider_failure` and write the Run_Manifest.
10. THE Loop_Orchestrator SHALL assign every Hypothesis, Claim, Claim revision, and Evidence record a unique identifier, and the Claim identifier SHALL stay the same across revisions of the same Claim.
11. WHEN a Hypothesis is received, THE Loop_Orchestrator SHALL assign the Origin `ai-inferred` to every Claim revision, set both Evidence_Statuses to `absent`, and leave the Approval status `none` as defined in Requirement 6.2, 6.4, and 6.14, regardless of any Origin, Evidence_Status, or approval-like value supplied by the AI (Requirement 6.16).
12. THE Loop_Orchestrator SHALL store the confidence and the open questions of each Claim exactly as the AI supplied them, SHALL label them as AI-stated, and SHALL NOT use them to set or change any Origin, any Evidence_Status, any Approval status, any Experiment_Policy decision, or any limit of Requirement 11.
13. WHEN a Claim is revised, THE Loop_Orchestrator SHALL store the revised confidence and open questions as part of the new revision record, and SHALL keep the earlier values in the Evidence_Store.
14. WHEN the Rule_Expression_Language evaluates an integer arithmetic expression, THE Rule_Expression_Language SHALL check every intermediate arithmetic result against the range −9007199254740991 to 9007199254740991 and, for the first intermediate result outside that range in evaluation order, SHALL return the evaluation error `overflow` with the JSON pointer of that node, even when a later operation would bring the value back into range, and SHALL NOT return a value computed from an imprecise number.
15. IF the Rule_Expression_Language evaluator receives an expression that the static validation of criterion 8 would reject for its structure (an unknown operator, a wrong number of arguments, a literal that is not a safe integer, string, boolean, or null, a missing or extra key, an invalid name, or a node that is not an object), THEN THE Rule_Expression_Language evaluator SHALL return the evaluation error `invalid_expression` with the JSON pointer of the offending node, SHALL NOT throw, and SHALL NOT return a value.
16. IF a response of the AI_Provider carries one of the names `origin`, `evidence`, `evidence_status`, `approval`, or `approved` at any nesting level other than the top level of a Claim (including the top level of the Hypothesis or of the response), THEN THE Loop_Orchestrator SHALL reject the whole response under criterion 8 and SHALL use no part of it. A name removed from the top level of a Claim under criterion 11, and a name in a rejected response, SHALL NOT change any Origin, any Evidence_Status, or any Approval status.
17. WHEN the Loop_Orchestrator removes authority-like properties from the top level of a Claim under criterion 11, THE Loop_Orchestrator SHALL treat a property name as authority-like if and only if, after conversion to lower case and deletion of every `_` and `-` character, the name equals `origin`, starts with `evidence`, ends with `evidencestatus`, or starts with `approv`, SHALL apply this matching to the direct property names of the Claim object only, and SHALL keep every other property of the Claim.
18. IF the Rule_Expression_Language evaluator catches an unexpected internal exception during evaluation, THEN THE Rule_Expression_Language evaluator SHALL return the evaluation error `internal_error` with the diagnostic cause `internal_fault`, SHALL NOT throw, SHALL NOT return a value, and SHALL NOT include exception text or a stack trace in the result. THE evaluation error `invalid_expression` of criterion 15 SHALL carry the diagnostic cause `structural`.
19. THE Rule_Expression_Language SHALL normalize the number `-0` to `0` in literals and in lookup-table values before use, so that no evaluation result is `-0`.
### Requirement 5: Citation Verification

**User Story:** As a Phoenix engineer, I want every source claim checked mechanically, so that citations are verifiable facts and not hallucinations.

#### Acceptance Criteria

1. THE Loop_Orchestrator SHALL require each Claim to carry between 1 and the configured Citation limit of Requirement 17.2 (default 5) Citations, and SHALL require each Citation to contain a file path, a start line, an end line, and quoted text, where:
   - both line numbers are integers of at least 1, counted from 1, and the start line is less than or equal to the end line;
   - the line range spans at most 100 lines;
   - the quoted text contains at least 1 non-whitespace character and at most 1000 Unicode code points.
2. WHEN a Claim is received or a Claim is revised, THE Citation_Verifier SHALL evaluate each Citation of the Claim in the following fixed order and SHALL stop at the first check that fails for that Citation:
   1. The Citation is well-formed according to criterion 1, otherwise the failure reason is `malformed_citation`.
   2. The file path equals, by case-sensitive character-for-character comparison with no path normalization, one path in the Source_Bundle manifest, otherwise the failure reason is `file_not_in_bundle`.
   3. The end line is less than or equal to the number of lines of the cited file, as counted under criterion 7, otherwise the failure reason is `range_out_of_bounds`.
   4. The quoted text, after the line-ending normalization of criterion 7, is a contiguous substring of the text of the cited line range, otherwise the failure reason is `quote_not_found`.
3. WHEN the Citation_Verifier has evaluated all Citations of a Claim, THE Citation_Verifier SHALL record in the Evidence_Store one verification result per Citation, with the value `verified` or `failed`, the failure reason from criterion 2 or criterion 9 for each failed Citation, and the identifiers of the Claim and its revision, regardless of whether other Citations of the Claim failed.
4. IF at least one Citation of a Claim has the result `failed`, THEN THE Citation_Verifier SHALL NOT remove or alter the Claim, and SHALL NOT change the Evidence records, Evidence_Statuses, or verification results of any other Claim; the `source` Evidence_Status of the Claim revision SHALL be set as defined in Requirement 6.5.
5. THE Citation_Verifier SHALL perform verification without any AI call, any network access, and any input other than the Claim, the Source_Bundle file contents, and the Source_Bundle manifest, so that identical inputs produce an identical verification result.
6. THE Citation_Verifier SHALL be the only component permitted to append a `source` Evidence record, and SHALL ignore any Origin, Evidence_Status, or approval-like value supplied by the AI.
7. THE Citation_Verifier SHALL apply the following text rules when it counts lines and compares quoted text:
   - Each CRLF sequence and each lone CR in both the cited file content and the quoted text is replaced with LF before any other step.
   - Line numbers are counted from 1 after this replacement, and a line ends at each LF.
   - A single LF at the end of the file does not start an additional line, and an empty file has 0 lines.
   - The text of a line range is the cited lines joined by LF, without the LF that ends the last cited line.
   - The comparison is an exact, case-sensitive, code-point-by-code-point match.
   - The comparison does not trim, collapse, or remove whitespace (spaces, tabs, and LF), and does not apply Unicode normalization, case folding, or comment or markup stripping to either side. A leading byte-order mark in a file is not removed.
   - The quoted text may start and end at any position within a line and may span several lines of the cited range.
8. WHEN all Citations of a Claim have the result `verified`, THE Citation_Verifier SHALL record that result in the Evidence_Store together with the Claim revision identifier, and THE Evidence_Store SHALL set the `source` Evidence_Status of the Claim revision to `supported` as defined in Requirement 6.5.
9. IF the content of a cited Source_Bundle file differs from the SHA-256 hash in the Source_Bundle manifest (computed after LF normalization as in Requirement 1.6), cannot be read, or is not valid UTF-8, THEN THE Citation_Verifier SHALL record `failed` with the reason `source_unavailable` for every Citation that cites that file.

### Requirement 6: Origin, Evidence, and Approval Model

**User Story:** As a Phoenix engineer, I want provenance, evidence, and human approval kept as three separate concepts, so that an observation of legacy behavior is never mistaken for a correct business specification and no record overwrites or hides another.

#### Acceptance Criteria

1. THE Evidence_Store SHALL record for every Claim revision exactly one Origin, with the value `ai-inferred` (the content was produced by the AI_Provider) or `human-authored` (the content was written by a human and not produced by the AI_Discovery_Loop). Origin SHALL describe only who produced the content of that Claim revision and SHALL NOT record any verification, observation, or approval.
2. THE Loop_Orchestrator SHALL create every Claim revision it stores with the Origin `ai-inferred` and SHALL NOT create the Origin `human-authored`. THE Origin of a stored Claim revision SHALL be immutable: IF any component requests a change of the Origin of a stored Claim revision, THEN THE Evidence_Store SHALL reject the request, leave the Origin byte-identical, and record the rejection with the component identity.
3. THE Evidence_Store SHALL record Evidence as separate, append-only Evidence records, each with a unique identifier, an Evidence_Kind, and the identifier of the one Claim revision it is linked to, and SHALL support exactly two Evidence_Kinds: `source` (Citation verification: the Source_Bundle contains the cited text) and `experiment` (Observations compared to Predictions: the observed behavior of the Legacy_App). IF a request to append an Evidence record names any other Evidence_Kind, THEN THE Evidence_Store SHALL reject it and leave all records unchanged.
4. THE Evidence_Store SHALL derive for every Claim revision one Evidence_Status per Evidence_Kind, with the value `absent`, `supported`, `contradicted`, or `mixed`, as a pure function of the Evidence records of that Evidence_Kind linked to that Claim revision (no other input, no wall-clock value, independent of the order in which the records were appended). WHEN a Claim revision is created, THE Evidence_Store SHALL set both Evidence_Statuses to `absent`.
5. WHEN the Citation_Verifier records a verification result for a Claim revision, THE Evidence_Store SHALL append one `source` Evidence record containing the per-Citation results, and SHALL set the `source` Evidence_Status of that Claim revision to `supported` if all Citations are `verified`, to `contradicted` if no Citation is `verified`, and to `mixed` if at least one but not all Citations are `verified`. THE Evidence_Store SHALL NOT change the `experiment` Evidence_Status or the Approval status of that Claim revision.
6. WHEN the Comparator records a result of `match` or `mismatch` for an Experiment that tests a Claim revision, THE Loop_Orchestrator SHALL append one `experiment` Evidence record for each tested Claim revision, with the outcome `supports` for `match` or `contradicts` for `mismatch`. THE Evidence_Store SHALL set the `experiment` Evidence_Status of each such Claim revision to `supported` (at least one `supports` outcome and no `contradicts` outcome), `contradicted` (at least one `contradicts` outcome and no `supports` outcome), or `mixed` (at least one outcome of each), counting `inconclusive` outcomes as neither. THE Evidence_Store SHALL NOT change the `source` Evidence_Status or the Approval status of that Claim revision.
7. WHEN the Comparator records `not_comparable` for an Experiment, THE Loop_Orchestrator SHALL append an `experiment` Evidence record with the outcome `inconclusive` for each tested Claim revision, and THE Evidence_Store SHALL leave the `experiment` Evidence_Status of those Claim revisions unchanged (a Claim revision whose only `experiment` records are `inconclusive` keeps the status `absent`).
8. THE Loop_Orchestrator SHALL interpret `source` Evidence only as evidence that the Source_Bundle contains the cited text, and `experiment` Evidence only as evidence of observed Legacy_App behavior. THE Loop_Orchestrator SHALL NOT interpret an Observation, either Evidence_Kind, or any combination of Evidence_Statuses (including `supported` for both kinds) as evidence that a Claim is a correct business specification.
9. THE Approval status of a Claim revision SHALL be derived only from the Approval_Records in the Approval_Store (Requirement 23) whose target is that Claim revision: `none` when no such record exists, otherwise the decision (`approved`, `rejected`, or `needs_changes`) of the record with the highest position in the hash chain among them. THE Loop_Orchestrator SHALL NOT use any value other than the Approval status `approved` to establish that a Claim is a correct business specification, and SHALL NOT derive, set, or cache an Approval status from Origin or Evidence data.
10. THE Evidence_Store and the Approval_Store SHALL track four facts independently for every Claim revision: Origin, `source` Evidence_Status, `experiment` Evidence_Status, and Approval status. Each of the four facts SHALL be queryable per Claim revision identifier. Every report that shows a Claim revision, including the output of the Loop_Orchestrator and of the Independent_Evaluator, SHALL show all four facts as four separate values and SHALL NOT merge, rank, or summarize them into one value.
11. THE Loop_Orchestrator SHALL have no interface that writes an Approval_Record, and SHALL NOT read the Approval_Store while it builds any AI_Provider payload.
12. THE Evidence_Store SHALL retain every Evidence record, including every record with outcome `contradicts` or `inconclusive`, as append-only data, and SHALL NOT remove, overwrite, summarize away, or omit any such record in later Claim revisions, Hypothesis revisions, Run_Manifest entries, or reports.
13. IF a Claim revision has at least one Evidence record with outcome `contradicts`, or an Evidence_Status of `contradicted` or `mixed`, THEN every report that shows that Claim revision SHALL show that Evidence_Status and the identifier of every contradicting Evidence record (with no cap on the count), in the same entry as, and not less prominent than, any `supported` Evidence_Status or `approved` Approval status of the same Claim revision.
14. WHEN a Claim is changed in a new revision, THE Evidence_Store SHALL create the new Claim revision with a new revision identifier, Origin `ai-inferred`, both Evidence_Statuses `absent`, and Approval status `none`. THE Evidence_Store SHALL keep the Evidence records and Approval_Records of all earlier revisions readable and linked to their own revision, and SHALL NOT copy, re-link, or carry over any Evidence record, Evidence_Status, or Approval status to the new revision, including when the new revision content is identical to an earlier revision.
15. IF any component other than the Citation_Verifier attempts to append a `source` Evidence record, or any component other than the rules of criteria 6 and 7 attempts to append an `experiment` Evidence record, THEN THE Evidence_Store SHALL reject the change, leave all records unchanged, and record the rejection with the component identity.
16. IF the AI supplies any Origin value, Evidence_Status value, or approval-like content in a Hypothesis or revision, THEN THE Loop_Orchestrator SHALL ignore the supplied value, apply criteria 2 and 14, and record in the Evidence_Store that a supplied value was discarded, without the discarded value (Requirement 23.6).
17. FOR ALL Claim revisions and ALL single updates of one of the four facts (appending a `source` Evidence record, appending an `experiment` Evidence record, or appending an Approval_Record), THE stored representation of the other three facts of that Claim revision, and of all four facts of every other Claim revision, SHALL be byte-identical before and after the update (independence property), and THE test suite SHALL verify this property over generated sequences of updates.
18. FOR ALL sets of Evidence records of one Evidence_Kind linked to one Claim revision, THE derived Evidence_Status SHALL be identical for every ordering of those records and for repeated derivation (determinism property), and THE test suite SHALL verify the derived value against the rules of criteria 4 to 7 for every combination of the outcomes `supports`, `contradicts`, and `inconclusive`, including the empty set.
19. IF a query of a fact names a Claim revision identifier that does not exist, THEN THE Evidence_Store SHALL return an error that identifies the identifier as unknown and SHALL NOT return a default value such as `absent` or `none`.

### Requirement 7: Experiment Generation

**User Story:** As a Phoenix engineer, I want the AI to propose Experiments that test specific Claims, so that each test has a stated purpose and an expected result.

#### Acceptance Criteria

1. WHEN a Hypothesis is accepted, THE Loop_Orchestrator SHALL send the accepted Hypothesis to the AI_Provider after a Payload_Audit and request at most the configured Experiment-per-response limit of Requirement 17.2 (default 10) Experiments.
2. THE Loop_Orchestrator SHALL validate each Experiment against a JSON schema before storing or using it. The schema SHALL require:
   - the identifier of the tested Claim or Hypothesis, which must match an identifier in the accepted Hypothesis;
   - a request sequence of 1 to 10 requests, each given as a Test_API operation with its input;
   - a Prediction containing an expected response status and at least one expected response field.
3. THE Experiment schema SHALL allow 0 to 10 declarative preparation steps. Each step SHALL describe a required starting state as data and SHALL contain no HTTP method, path, URL, or header. Only the Experiment_Runner SHALL execute preparation steps, by selecting the Test_API operations itself (Requirement 9.10).
4. IF an Experiment fails schema validation, THEN THE Loop_Orchestrator SHALL reject it, record the validation errors in the Evidence_Store, not pass it to the Experiment_Runner, and keep every other Experiment in the same AI response that passed validation.
5. THE Experiment schema SHALL reject any Experiment whose request sequence or preparation steps specify the reset operation (`POST /reset`) or the state-transition test operation (`POST /test/orders/{id}/ship`) of the Test_API. Only the Experiment_Runner SHALL invoke these operations, and only as part of its own run control.
6. THE Experiment schema SHALL contain no field name, enumeration value, or example that names a specific business rule of the Legacy_App.
7. IF a validated Experiment does not cite the identifier of an existing Claim or Hypothesis, or cites an identifier that does not exist in the accepted Hypothesis, THEN THE Loop_Orchestrator SHALL reject it, record the reason, and not pass it to the Experiment_Runner.
8. IF the AI_Provider returns no Experiment that passes schema validation, THEN THE Loop_Orchestrator SHALL record that outcome in the Evidence_Store and apply the termination rule of Requirement 11.14.

### Requirement 8: Experiment_Policy

**User Story:** As a Phoenix engineer, I want every Experiment validated by a deterministic policy, so that the AI can only trigger permitted operations.

#### Acceptance Criteria

1. THE Experiment_Policy SHALL define an allowlist of Test_API operations as exact pairs of an uppercase HTTP method and a path pattern, and SHALL reject any request whose method and path, compared as received without normalization, decoding, or case folding, do not match an entry.
2. WHEN an Experiment is submitted, THE Experiment_Policy SHALL evaluate every request and every declared preparation step of the Experiment before execution, using only the Experiment content and the Experiment_Policy configuration, without any AI call, network call, or clock value, and SHALL record in the Evidence_Store exactly one decision of `accept` or `reject`, the Experiment identifier, and the identifier of every violated rule in a fixed order.
3. THE Experiment_Policy SHALL accept an Experiment only if all of its requests and preparation steps pass all rules, and SHALL return an identical decision and identical reason list for identical Experiment content and identical configuration.
4. IF an Experiment contains a request for `POST /reset`, including a path that matches it after case folding, percent-decoding, trailing-slash removal, or query-string removal, THEN THE Experiment_Policy SHALL reject the Experiment, even if the allowlist would otherwise match.
5. IF an Experiment contains a request for `POST /test/orders/{id}/ship`, where `{id}` is any value, including a path that matches it after case folding, percent-decoding, trailing-slash removal, or query-string removal, THEN THE Experiment_Policy SHALL reject the Experiment, even if the allowlist would otherwise match.
6. IF the Experiment_Policy configuration lists `POST /reset` or `POST /test/orders/{id}/ship` in the allowlist, is missing, is malformed, or fails to load, THEN THE Experiment_Policy SHALL reject every Experiment and the Loop_Orchestrator SHALL refuse to start the Run.
7. IF an Experiment contains an absolute URL, a host other than the configured Test_API base address, a path traversal sequence (`..`, or its percent-encoded form), or a header whose name is not in a fixed header allowlist, THEN THE Experiment_Policy SHALL reject the Experiment.
8. IF an Experiment exceeds the configured limits for request count (default 10 per Experiment), request body size (default 8192 bytes per request), or declared preparation steps (default 10 per Experiment), THEN THE Experiment_Policy SHALL reject the Experiment.
9. IF an Experiment_Policy decision cannot be computed, THEN THE Experiment_Policy SHALL reject the Experiment with a reason indicating an evaluation failure, and SHALL NOT pass it to the Experiment_Runner.
10. WHEN the Experiment_Policy rejects an Experiment, THE Loop_Orchestrator SHALL NOT count it toward the Run Experiment limit of Requirement 11.7, SHALL count only Experiments accepted by the Experiment_Policy toward that limit, and SHALL NOT execute, retry, or repair the rejected Experiment.
11. THE Loop_Orchestrator SHALL count every rejected Experiment toward a separate configurable per-Run limit on rejected Experiments (default 20), and WHEN that limit is reached, THE Loop_Orchestrator SHALL stop the Run with termination reason `policy_rejection_limit` and write the Run_Manifest.
### Requirement 9: Experiment_Runner Execution

**User Story:** As a Phoenix engineer, I want a deterministic runner to execute Experiments, so that the AI never touches the Legacy_App, Docker, the file system, Git, or the network directly.

#### Acceptance Criteria

1. WHEN the Experiment_Runner is started, THE Experiment_Runner SHALL check the health of the Legacy_App through the Test_API and SHALL treat the Legacy_App as healthy only if a successful response arrives within 10 seconds. IF the Legacy_App is not healthy within that time, THEN THE Experiment_Runner SHALL stop with an error indicating the Legacy_App is unhealthy, SHALL record the failure in the Evidence_Store, and SHALL execute no Experiment.
2. WHEN the Experiment_Runner receives an Experiment, THE Experiment_Runner SHALL execute it only if the Evidence_Store holds exactly one Experiment_Policy `accept` decision for that Experiment identifier.
3. IF an Experiment has no recorded Experiment_Policy `accept` decision, or its recorded decision is `reject`, THEN THE Experiment_Runner SHALL NOT execute the Experiment, SHALL send no request to the Legacy_App for it, and SHALL record the Experiment as `not_executed` with the reason `policy_not_accepted`.
4. THE Experiment_Runner SHALL send a request to the Legacy_App only WHILE the Run holds the Run_Lock and the runtime holds a valid Run_Lease issued by the Launcher for that Run (Requirement 24). THE Run_Lock SHALL cover the whole Run, so THE Experiment_Runner SHALL NOT acquire or release a lock per Experiment.
5. IF the Run_Lease is missing, invalid, or revoked when an Experiment is about to start, or at any later point before a request of that Experiment is sent, THEN THE Experiment_Runner SHALL send no further request to the Legacy_App for that Experiment. IF no request of the Experiment's request sequence has been sent, THEN THE Experiment_Runner SHALL record the Experiment as `not_executed` with the reason `lease_unavailable`. IF at least one request of the request sequence has been sent, THEN THE Experiment_Runner SHALL record the Experiment as `aborted` with the reason `lease_unavailable` and the responses collected so far.
6. UNTIL the mechanical lock of Requirement 24 is implemented, concurrent execution of the AI_Discovery_Loop and the Ground_Truth conformance runner SHALL be prohibited by procedure (Requirement 24.1).
7. THE Experiment_Runner SHALL execute at most 1 Experiment at a time, and SHALL execute the Experiments of a Run sequentially in the order the Loop_Orchestrator submitted them.
8. WHEN the Experiment_Runner starts an accepted Experiment, THE Experiment_Runner SHALL call the reset operation of the Test_API before any other request of that Experiment and SHALL confirm that the reset operation returned a successful response within the per-request time limit.
9. IF the reset operation fails, returns an unsuccessful response, or is not confirmed within the per-request time limit, THEN THE Experiment_Runner SHALL NOT execute any preparation step or request of the Experiment and SHALL record the Experiment as `not_executed` with the reason `reset_failed`.
10. WHEN an accepted Experiment has declarative preparation steps, THE Experiment_Runner SHALL translate each step, in declared order, into Test_API operations that the Experiment_Runner itself selects from a fixed runner-owned preparation table (which may include the state-transition test operation), SHALL execute them after the confirmed reset and before the request sequence, and SHALL record each operation performed with its response status.
11. THE Experiment_Runner SHALL NOT insert, load, or execute SQL fixtures or any direct database statement for an AI-proposed Experiment, and SHALL reach the database state only through the Test_API.
12. IF a declarative preparation step is not present in the preparation table, or a translated operation does not return a successful response within the per-request time limit, THEN THE Experiment_Runner SHALL NOT execute the request sequence of the Experiment and SHALL record the Experiment as `not_executed` with the reason `preparation_failed`, the identifier of the failing step, and the recorded response status (or the value `none` if no response arrived).
13. WHEN the Experiment_Runner executes the request sequence of an Experiment, THE Experiment_Runner SHALL send the requests one at a time in declared order, and SHALL record each request and each response (status and body) as the Observation, together with the state-check responses of the Experiment, and SHALL then record the Experiment as `executed`.
14. THE Experiment_Runner SHALL apply a per-request time limit (default 10 seconds; permitted range 1 to 60 seconds) and a per-Experiment time limit (default 60 seconds; permitted range 1 to 600 seconds; covering reset, preparation, and request sequence), both changeable by configuration. IF a configured value is outside its range, or the per-Experiment limit is smaller than the per-request limit, THEN THE Experiment_Runner SHALL refuse to start and SHALL execute no Experiment.
15. IF a per-request or per-Experiment time limit is exceeded, THEN THE Experiment_Runner SHALL abort the Experiment and SHALL send no further request for it. IF the limit is exceeded during reset or preparation, THEN THE Experiment_Runner SHALL record the Experiment as `not_executed` with the reason `reset_failed` or `preparation_failed` respectively. IF the limit is exceeded during the request sequence, THEN THE Experiment_Runner SHALL record the Experiment as `timed_out` with the responses collected so far.
16. THE Experiment_Runner SHALL send every request, including the health check, reset, preparation operations, and request-sequence requests, only to the loopback-published Reverse_Proxy address or the configured internal Test_API address (Requirement 18.2). IF a request is about to be sent to any other address, THEN THE Experiment_Runner SHALL NOT send it, SHALL abort the Experiment, and SHALL record the Experiment as `not_executed` (no request-sequence request sent) or `aborted` (otherwise) with the reason `address_not_allowed`.
17. IF the Experiment_Runner is configured with a Test_API address that is neither the loopback-published Reverse_Proxy address nor the configured internal Test_API address, THEN THE Experiment_Runner SHALL refuse to start, SHALL record the configured address in the Evidence_Store, and SHALL send no request to the Legacy_App (Requirement 18.3).
18. THE AI_Provider SHALL have no access to the Experiment_Runner other than through Experiments that passed schema validation and the Experiment_Policy.

### Requirement 10: Prediction and Observation Comparison

**User Story:** As a Phoenix engineer, I want Predictions compared to Observations deterministically, so that results are objective.

#### Acceptance Criteria

1. WHEN an Observation is recorded for an Experiment, THE Comparator SHALL compare the Prediction of that Experiment to the Observation without any AI call.
2. THE Comparator SHALL mask every field whose path appears in a configured list of non-deterministic field paths, replacing its value with one fixed mask token, in both the Prediction and the Observation before comparison.
3. THE Comparator SHALL compare the response status code and each predicted field by exact value and exact type after masking, with no type coercion, no case folding, no whitespace trimming, and no numeric tolerance.
4. THE Comparator SHALL ignore any Observation field that the Prediction does not name.
5. WHEN every predicted status code and predicted field equals the corresponding Observation value after masking, THE Comparator SHALL record the result `match`.
6. IF any predicted status code or predicted field differs from the Observation after masking, or a predicted field is absent from the Observation, THEN THE Comparator SHALL record the result `mismatch` with a field-level difference list.
7. THE Comparator SHALL list each difference with the field path, the predicted value, and the observed value (or an absent marker), and SHALL order the list by field path in ascending code-point order, with the status code difference first.
8. WHEN an Experiment is recorded as `not_executed`, `timed_out`, or `aborted`, THE Comparator SHALL record the result `not_comparable` with the reason `not_executed`, `timed_out`, or `aborted` respectively.
9. IF the Prediction is missing, the Observation body cannot be parsed as structured data for a predicted field, or the masking configuration is missing or invalid, THEN THE Comparator SHALL record the result `not_comparable` with a reason that names the cause, and SHALL NOT record `match` or `mismatch`.
10. THE Comparator SHALL record each comparison result in the Evidence_Store, linked to the Experiment identifier, the Prediction, and the Observation, and SHALL NOT modify the Prediction or the Observation.
11. FOR ALL Predictions and Observations, comparing the same Prediction, the same Observation, and the same masking configuration repeatedly SHALL produce byte-identical results, with no wall-clock value or random value in the result (idempotence).
12. FOR ALL Observations, applying masking to an already masked Observation SHALL produce an output identical to the masked Observation (masking idempotence).
13. THE comparison result SHALL be the only basis for `experiment` Evidence records (Requirement 6.6 and 6.7), and THE Comparator SHALL NOT create, change, or imply a `source` Evidence record, an Origin, or an Approval_Record; a `match` result SHALL be reported as agreement with observed Legacy_App behavior and SHALL NOT be reported as business-specification correctness.

### Requirement 11: Hypothesis Update and Loop Control

**User Story:** As a Phoenix engineer, I want the AI to revise Hypotheses from Observations within strict limits, so that the loop converges and always terminates.

#### Acceptance Criteria

1. WHEN the Comparator has recorded a result for every Experiment of an Iteration, THE Loop_Orchestrator SHALL pass the current Hypothesis and the comparison results of that Iteration through the Payload_Audit and, if the audit passes, send them to the AI_Provider with a request for a revised Hypothesis.
2. THE Loop_Orchestrator SHALL build the payload of each Hypothesis update request only from the current Hypothesis, the Source_Bundle, and the Iteration's Experiments, Predictions, Observations, and comparison results.
3. THE Loop_Orchestrator SHALL NOT include Ground_Truth content, Migration_Decisions content, Conformance_Baseline content, review package content, or Independent_Evaluator results in any payload sent to an AI_Provider, in any Iteration of any Run.
4. WHEN the AI_Provider returns a revised Hypothesis, THE Loop_Orchestrator SHALL validate it against the Hypothesis schema (Requirement 4) and the Citation_Verifier SHALL verify its Citations (Requirement 5) before the Loop_Orchestrator uses it.
5. WHEN a revised Hypothesis passes validation, THE Loop_Orchestrator SHALL store it as a new revision that records the identifier of its predecessor revision and the identifiers of the Evidence records that prompted the revision.
6. IF a revised Hypothesis fails schema validation, THEN THE Loop_Orchestrator SHALL reject it, record the validation errors, keep the predecessor revision as the current Hypothesis, and count the attempt against the retry limit of criterion 10.
7. THE Loop_Orchestrator SHALL apply default limits of 3 Iterations and 20 Experiments in total per Run, counted across all Iterations, where an Experiment counts once it is accepted by the Experiment_Policy, and SHALL accept configured integer values of 1 to 10 for the Iteration limit and 1 to 100 for the Experiment limit.
8. IF a configured limit is missing, non-integer, or outside its permitted range, THEN THE Loop_Orchestrator SHALL refuse to start the Run, report the invalid setting, and use no default silently in place of an invalid value.
9. WHEN accepting the next Experiment would exceed the Experiment limit, THE Loop_Orchestrator SHALL not execute that Experiment, SHALL finish the Experiments already accepted without a further AI_Provider call, and SHALL stop the Run with termination reason `experiment_limit_reached`.
10. THE Loop_Orchestrator SHALL apply configurable limits for total Run time, per-call time of an AI_Provider call, and retries per AI_Provider call, with defaults of 1800 seconds, 120 seconds, and 2 retries (3 attempts in total), respectively.
11. WHEN the Iteration limit is reached after the comparison of the last permitted Iteration, THE Loop_Orchestrator SHALL stop the Run with termination reason `iteration_limit_reached`, SHALL NOT start a further Iteration, and SHALL NOT make a further AI_Provider call (Requirement 11.18).
12. WHEN the total Run time limit is reached, THE Loop_Orchestrator SHALL stop starting new AI_Provider calls and new Experiments, and SHALL stop the Run with termination reason `time_limit_reached` within 30 seconds.
13. IF an AI_Provider call fails or exceeds the per-call time limit on every permitted attempt, THEN THE Loop_Orchestrator SHALL stop the Run with termination reason `provider_failure`, saving the final state of criterion 18 and keeping all Evidence records.
14. WHEN an Iteration produces no new accepted Experiment, THE Loop_Orchestrator SHALL stop the Run with termination reason `no_further_experiments`.
15. IF any other unrecoverable error occurs, THEN THE Loop_Orchestrator SHALL stop the Run with termination reason `error`, record the error, and not send any further AI_Provider request.
16. WHEN a Run stops for any termination reason, THE Loop_Orchestrator SHALL record exactly one termination reason from the values `iteration_limit_reached`, `experiment_limit_reached`, `time_limit_reached`, `no_further_experiments`, `provider_failure`, `payload_audit_blocked` (Requirement 2.10), `policy_rejection_limit` (Requirement 8.11), `isolation_violation` (Requirement 15.6), `lease_unavailable` (Requirement 24.15), `launcher_killed` (Requirement 24.12), and `error`, and SHALL write the Run_Manifest, including the effective limit values and the counts of Iterations and Experiments used.
17. THE Loop_Orchestrator SHALL terminate every Run in finite time, bounded by the total Run time limit plus 30 seconds, for every provider behavior including the Mock_Provider.
18. WHEN any limit of this requirement or of Requirement 8.11 is reached (Iteration limit, Experiment limit, total Run time limit, rejected-Experiment limit, or AI_Provider retry limit), THE Loop_Orchestrator SHALL make no new AI_Provider call and SHALL NOT make a closing revision call, SHALL save as the final state the last Hypothesis revision that passed schema validation and Citation verification, and THE Run_Manifest SHALL name that revision by its identifier (or the value `none` when no revision passed). Comparison results of Experiments executed after that revision SHALL be kept as Evidence records and SHALL NOT be summarized into a new revision.

### Requirement 12: Evidence_Store and Run_Manifest

**User Story:** As a Phoenix engineer, I want every Run recorded in an append-only, hash-verified store, so that decisions are traceable and reproducible.

#### Acceptance Criteria

1. WHEN a Run starts, THE Launcher SHALL create the Run_Volume dedicated to that Run, where `<run-id>` differs from the name of every existing directory under `discovery/runs/` (including `discovery/runs/.incoming/`) and from the identifier of every existing Run_Volume, and THE Evidence_Store SHALL write the Run records into that Run_Volume.
2. IF a directory `discovery/runs/<run-id>/`, a directory `discovery/runs/.incoming/<run-id>/`, or a Run_Volume for `<run-id>` already exists when a Run starts, THEN THE Launcher SHALL refuse to start the Run, leave the existing directory or volume unchanged, and report an error that identifies the colliding `<run-id>`.
3. THE Evidence_Store SHALL record the following for every Run, each as a separate record: the Source_Bundle manifest, every audited payload with its SHA-256 hash, every AI output, every Experiment, every Experiment_Policy decision with its reason, every Observation, every comparison result, every Evidence record, every Evidence_Status change, every Origin assignment, every discarded AI-supplied status or approval-like value, and every Hypothesis revision. THE Run directory SHALL contain no Approval_Record.
4. THE Evidence_Store SHALL assign each record a record identifier that is unique within the Run and a sequence number. Sequence numbers SHALL start at 1 and increase by exactly 1 with no gaps.
5. IF the AI_Discovery_Loop requests the modification or deletion of a record that has been written, THEN THE Evidence_Store SHALL reject the request, leave the record byte-identical, and append a record of the rejection.
6. THE Evidence_Store SHALL store in each record the SHA-256 hash of the immediately preceding record. The first record of a Run SHALL store a fixed genesis value of 64 zero characters in place of a predecessor hash.
7. THE Evidence_Store SHALL record, for each Claim, an ordered list of revisions. Each revision SHALL carry a revision number starting at 1, the identifier of its predecessor revision, the reason for the change, and the identifiers of the Evidence records linked to it. Earlier revisions SHALL remain retrievable after later revisions are written.
8. WHEN a Run terminates for any termination reason, THE Evidence_Store SHALL write exactly one Run_Manifest into the Run_Volume. The Run_Manifest SHALL list every Run artifact by relative path and SHA-256 hash (lowercase hexadecimal), and SHALL include the Run configuration, limits, provider identity, tool versions, termination reason, total record count, and the hash of the last record in the chain.
9. WHEN the verification operation is invoked on a Run_Volume, an Incoming_Export, or a Run directory, THE Evidence_Store SHALL recompute every artifact hash and every chain link, SHALL compare the file list with the Run_Manifest, and SHALL treat the Completion_Marker, the Reason_File, and the Launcher record of criterion 22 as the only files that the Run_Manifest need not list. For each mismatch it SHALL report the record identifier or path and the mismatch kind (`modified`, `missing`, `unlisted`, or `chain_break`). It SHALL return a failure result if one or more mismatches exist, and a success result otherwise.
10. WHEN the verification operation is invoked, THE Evidence_Store SHALL NOT modify any file in the Run directory.
11. IF a Run_Volume, an Incoming_Export, or a Run directory has no Run_Manifest, or a Run directory has no Completion_Marker, THEN the verification operation SHALL return a failure result that reports the Run as `incomplete`.
12. THE repository `.gitignore` SHALL list `discovery/runs/`, so that raw Run records are not tracked by Git unless a human selects specific records for commit.
13. IF a record to be stored contains a value that matches a configured secret pattern, including the value of an environment variable, THEN THE Evidence_Store SHALL reject the whole record and write no part of it. It SHALL append a rejection record that names the matched pattern and omits the matched value.
14. IF a record write to the Run_Volume fails, THEN THE Evidence_Store SHALL leave no partially written record visible to the verification operation and SHALL signal an unrecoverable error to the Loop_Orchestrator (Requirement 11.15).
15. FOR ALL stored records, serializing, storing, loading, and parsing SHALL produce a record equal to the original (round-trip property).
16. WHEN a report or the Independent_Evaluator reads Approval_Records for a Claim revision of a Run, THE reader SHALL read them only from the Approval_Store (Requirement 23), and THE Run_Manifest SHALL NOT list Approval_Records as Run artifacts.
17. WHILE a Run is in progress, THE runtime SHALL write the Run records only to the Run_Volume, and THE runtime container SHALL have no Windows bind mount that receives Run records.
18. WHEN the runtime container has stopped (Requirement 24.11), THE Launcher SHALL copy the Run records from the Run_Volume to the Incoming_Export `discovery/runs/.incoming/<run-id>/`, and THE Launcher SHALL create that export directory only after the Run has ended.
19. WHEN the copy of criterion 18 has finished, THE Launcher SHALL run the verification operation of criterion 9 on the Incoming_Export, checking the file list and every SHA-256 hash against the Run_Manifest and the hash chain.
20. WHEN the verification of criterion 19 succeeds, THE Launcher SHALL move the Run to the completed state by placing the export at `discovery/runs/<run-id>/` and writing the Completion_Marker, which contains the SHA-256 hash of the Run_Manifest, as the last file written. THE Launcher SHALL NOT assume that a directory rename on the Windows file system is atomic, and the completed state SHALL be established only by the Completion_Marker together with a Run_Manifest that verifies.
21. IF the copy, the verification, the move, or the writing of the Completion_Marker fails, THEN THE Launcher SHALL keep the Run as `incomplete`, SHALL write no Completion_Marker (or SHALL remove a Completion_Marker that was written before the failure was detected), SHALL write a Reason_File that names the failing step, and SHALL NOT present the Run as complete.
22. THE Launcher SHALL remove the Run_Volume only after a successful verification under criterion 19, and SHALL keep the Run_Volume for diagnosis when any step of criteria 18 to 20 fails or when the Launcher is killed. THE Launcher SHALL record which of the two applied (`removed_after_verified_export` or `kept_for_diagnosis`) in a Launcher record next to the export, and the Launcher record SHALL NOT be a Run artifact listed in the Run_Manifest.
23. WHEN the Independent_Evaluator, the reproducibility check of Requirement 22.7, or the replay of Requirement 22.4 reads a Run directory, THE reader SHALL accept the Run only if the Completion_Marker exists, its recorded hash equals the SHA-256 hash of the Run_Manifest, and the verification operation of criterion 9 succeeds; otherwise THE reader SHALL treat the Run as `incomplete`.
24. THE reader of a Run SHALL ignore every directory under `discovery/runs/.incoming/` as a source of complete Runs, and THE test suite SHALL verify, with a positive control (a complete Run that is accepted), that a Run with a missing Completion_Marker, a Completion_Marker whose hash differs from the Run_Manifest hash, or a failing verification is rejected as `incomplete`.
### Requirement 13: Independent_Evaluator Process and Inputs

**User Story:** As a Phoenix engineer, I want an evaluator separate from the runtime, so that scoring is independent and the answer cannot leak into the loop.

#### Acceptance Criteria

1. THE Independent_Evaluator SHALL run as an operating-system process that is separate from the Loop_Orchestrator process, and SHALL NOT share memory with it or be invoked in-process by it.
2. THE Independent_Evaluator SHALL open for reading only these files: the Completion_Marker and the artifacts listed in the Run_Manifest of the Run being scored, `evaluation/ground-truth/ground-truth.json`, `evaluation/migration-decisions.json`, the Conformance_Baseline, the Approval_Store (`discovery/approvals/`, read-only, because reports must show the Approval status per Requirement 6.10), and its own configuration.
3. THE Independent_Evaluator SHALL NOT start, reset, or send any request to the Legacy_App, and SHALL NOT start or control any Docker container, consistent with the Spec_Restoration_Evaluation rule of the legacy-sample spec.
4. WHEN the Independent_Evaluator starts, THE Independent_Evaluator SHALL first check that the Completion_Marker exists in the Run directory and that its recorded hash equals the SHA-256 hash of the Run_Manifest, and THEN SHALL recompute the SHA-256 hash of every artifact listed in the Run_Manifest and the hash chain of the Evidence_Store, and SHALL compare them with the recorded values before computing any score.
5. IF the Completion_Marker hash differs from the Run_Manifest hash, any recomputed hash differs from the Run_Manifest or the hash chain, a listed artifact is missing, or a file exists in the Run directory that the Run_Manifest does not list (other than the Completion_Marker, the Reason_File, and the Launcher record of Requirement 12.22), THEN THE Independent_Evaluator SHALL refuse to score the Run, SHALL exit with a non-zero exit status, SHALL write an error report that names each mismatching, missing, or unlisted artifact, and SHALL produce no score.
6. IF the Run directory contains no Run_Manifest or no Completion_Marker, THEN THE Independent_Evaluator SHALL refuse to score the Run as `incomplete`, SHALL exit with a non-zero exit status, and SHALL produce no score. THE Independent_Evaluator SHALL NOT read a Run_Volume or an Incoming_Export.
7. IF `evaluation/ground-truth/ground-truth.json` is missing, unreadable, not valid JSON, or not in the approved state recorded in its authoring metadata, THEN THE Independent_Evaluator SHALL exit with a non-zero exit status and SHALL produce no score.
8. THE Independent_Evaluator SHALL be located outside the runtime packages (proposed `evaluation/spec-restoration-evaluator/`), and no runtime module SHALL import it or invoke it.
9. THE Independent_Evaluator SHALL write its results to a location that is outside every Run directory and that does not overwrite the Ground_Truth, Migration_Decisions, Conformance_Baseline, or any Compatibility_Evaluation or Ground_Truth_Conformance_Run result file.
10. THE Independent_Evaluator SHALL NOT create, modify, or delete any file inside a Run directory or any of its input files.
11. FOR ALL identical inputs (Run artifacts, Ground_Truth, Migration_Decisions, Conformance_Baseline), THE Independent_Evaluator SHALL produce byte-identical output across at least 2 executions, with no wall-clock value, random value, process identifier, or absolute host path in the output.
12. THE Independent_Evaluator SHALL label its results as Spec_Restoration_Evaluation, and SHALL record them separately from Compatibility_Evaluation and Ground_Truth_Conformance_Run results.
13. IF the Approval_Store hash chain fails verification (Requirement 23.9), THEN THE Independent_Evaluator SHALL refuse to score the Run, SHALL exit with a non-zero exit status, and SHALL produce no score.

### Requirement 14: Two-Axis Evaluation

**User Story:** As a project owner, I want the result scored on legacy fidelity and on target-specification agreement separately, so that a faithful restoration of a defect is not confused with correctness.

#### Acceptance Criteria

1. THE Independent_Evaluator SHALL compute Legacy_Behavior_Restoration (axis A) per scoring unit by comparing the Prediction for that unit with the observed legacy behavior recorded for that unit in the Conformance_Baseline, and SHALL read no other source of legacy behavior. A scoring unit is one of the scenario units or boundary cases of the Ground_Truth.
2. IF the Conformance_Baseline holds no recorded observed legacy behavior for a scoring unit (for example, a unit recorded as not executed), THEN THE Independent_Evaluator SHALL report that unit as `baseline_not_covered` on axis A, SHALL exclude it from the axis A numerator and denominator, and SHALL list its identifier in the output. THE Independent_Evaluator SHALL NOT create, derive, or infer a legacy observation for it.
3. THE Independent_Evaluator SHALL compute Target_Specification_Alignment (axis B) per scoring unit by comparing the Prediction for that unit with the expected specification of that unit in the Ground_Truth and, for a unit covered by a decision in the Migration_Decisions, with the approved target recorded in that decision.
4. WHEN the Independent_Evaluator scores a Run, THE Independent_Evaluator SHALL derive the Prediction for each scoring unit deterministically, without any AI call, from the structured Claims of the final Hypothesis revision of the Run, as follows:
   - (a) A Claim applies to a unit if and only if its condition expression evaluates to true over the request inputs of that unit as recorded in the Conformance_Baseline, using the Rule_Expression_Language of Requirement 4.6.
   - (b) The Prediction is the union of the expected responses (response status and response fields) of all applying Claims, with each expression evaluated over the same inputs.
   - (c) If two applying Claims give different values for the same status or field, THE Independent_Evaluator SHALL mark that status or field `conflicting`, and it SHALL NOT count it as correct on either axis.
   - (d) If a Claim expression cannot be evaluated for a unit (for example, a lookup that has no entry for an input), THE Independent_Evaluator SHALL treat the Claim as not applying and SHALL record the reason.
5. THE Independent_Evaluator SHALL score a scoring unit on an axis as `correct` if and only if the Prediction contains the response status and every response field of the reference record for that axis, and each value equals the reference value by exact comparison after masking the fields listed in the Ground_Truth non-deterministic field list. THE Independent_Evaluator SHALL score a unit with at least one applying Claim that does not meet this condition as `incorrect`.
6. THE Independent_Evaluator SHALL report a scoring unit that no Claim applies to as `uncovered` with the reason code `no_applying_claim`, SHALL NOT count it as `correct`, and SHALL keep it in the denominator of each axis for which a reference record exists.
7. WHEN a scenario is an Approved_Divergence, THE Independent_Evaluator SHALL score axis A against the legacy response and axis B against the approved target independently. Both scores SHALL be derived from the same Prediction, so that a Prediction matching only the legacy response scores `correct` on axis A and `incorrect` on axis B, and a Prediction matching only the approved target scores the reverse.
8. THE Independent_Evaluator SHALL report the Approved_Divergence scenarios as a separate list with one entry per Approved_Divergence, each showing the scenario identifier, the decision identifier, the axis A score, the axis B score, and the reference values of both axes.
9. THE Independent_Evaluator SHALL report axis A and axis B each as a count of `correct` units, a denominator, and counts of `incorrect`, `uncovered`, and `baseline_not_covered` units, with the `uncovered` count broken down by reason code. THE Independent_Evaluator SHALL NOT report a single merged score unless both axis values are reported next to it.
10. THE Independent_Evaluator SHALL report, per scoring unit, the applying Claim revisions with, for each, the four facts of Requirement 6.10 shown separately (Origin, `source` Evidence_Status, `experiment` Evidence_Status, and Approval status read from the Approval_Store), and the Evidence records that support or contradict them. THE Independent_Evaluator SHALL report the applying Claim revisions that have no supporting evidence (neither Evidence_Status is `supported`) in a list separate from the other applying Claim revisions, and SHALL NOT treat an Approval status as supporting evidence in that classification.
11. IF the Conformance_Baseline or Migration_Decisions are missing, malformed, or inconsistent with the Ground_Truth (including a scenario identifier present in one and absent in another, or a number of Approved_Divergence entries that differs from the number of decided `follow_expected_specification` decisions), THEN THE Independent_Evaluator SHALL stop with an error indicating the failing input, SHALL produce no score, and SHALL leave the Run artifacts unmodified.
12. FOR ALL identical inputs, THE Independent_Evaluator SHALL produce byte-identical axis A and axis B results, including the per-unit lists.
13. WHEN a scoring unit cannot be reproduced by Experiments, including a Ground_Truth boundary case that used a temporary fixture product that is not in the seed data, THE Independent_Evaluator SHALL report the unit as `uncovered` with the reason code `fixture_not_reproducible`, SHALL keep it in the denominator, and SHALL show it in a separate list so that it is not mistaken for an AI error.
14. WHEN a scoring unit needs a request body that is not JSON or needs control of the lexical form of a number (for example the number of digits, a leading sign, or an exponent form), THE Independent_Evaluator SHALL report the unit as `uncovered` with the reason code `unsupported_request_form`, SHALL keep it in the denominator, and SHALL show it in the separate list of criterion 13. THE MVP does not support these forms.
15. THE Independent_Evaluator report SHALL list the limitations of criteria 13 and 14 in an evaluation-limitations section that names every affected unit and its reason code, and THE Independent_Evaluator SHALL NOT present an affected unit as an AI failure without that note.

### Requirement 15: Evaluation Isolation from the Runtime

**User Story:** As a Phoenix engineer, I want the runtime loop technically unable to read the answer, so that isolation does not depend on path-name checks alone.

#### Acceptance Criteria

1. THE Loop_Orchestrator, Source_Bundler, Experiment_Runner, Payload_Auditor, Citation_Verifier, Comparator, Evidence_Store, and every AI_Provider SHALL have no import path, direct or transitive, to the Independent_Evaluator or to any module that reads the Ground_Truth, the Migration_Decisions, the Conformance_Baseline, `evaluation/review/`, or `evaluation/results/`.
2. WHILE the AI_Discovery_Loop executes, THE Loop_Orchestrator process SHALL run under an operating-system-level or container-level access boundary (separate unprivileged OS account, process separation, or container mounts) that denies read, list, and stat access to `evaluation/`, and THE denial SHALL NOT depend on path-string checks in code.
3. WHILE the AI_Discovery_Loop executes, THE runtime environment SHALL contain no mount, volume, symbolic link, junction, hard link, or environment variable that references the Ground_Truth, the Migration_Decisions, the Conformance_Baseline, `evaluation/review/`, or `evaluation/results/`.
4. THE Independent_Evaluator SHALL run only after the Run has terminated, the Run_Manifest has been written, and the Run has been exported and marked complete with the Completion_Marker (Requirement 12.20), and SHALL run under access rights that grant read access to `evaluation/` and to the Run directory and no write access to the Run directory.
5. THE Loop_Orchestrator SHALL NOT feed any evaluation result, score, or Independent_Evaluator output into any Iteration, any AI_Provider payload, or any later Run, and no runtime configuration SHALL name an evaluation output location as an input.
6. IF a runtime component attempts to read an evaluation output or an evaluation input, THEN THE operating system or container boundary SHALL deny the read with a permission or not-found error, and THE Loop_Orchestrator SHALL record the denied attempt and stop the Run with termination reason `isolation_violation`.
7. WHEN the test suite runs, THE test suite SHALL verify the absence of import paths from runtime modules to evaluation modules by static dependency analysis, and SHALL include a positive control: a deliberately added import of an evaluation module in a test fixture must be reported as a violation.
8. WHEN the test suite runs, THE test suite SHALL verify, by read, list, and stat attempts executed under the runtime access rights, that each protected location under `evaluation/` is denied, and SHALL include a positive control: the same attempts executed under the evaluator access rights must succeed, so that a denial caused by a missing file or a wrong path is not counted as a pass.
9. WHEN the test suite runs, THE test suite SHALL verify that a Run completed with the Mock_Provider leaves no Ground_Truth canary and no decoy canary in any Run artifact, any audited payload, or any log, and SHALL include a positive control: a Run that is deliberately seeded with a canary through a test-only channel must be detected by the same scan.
10. WHEN the test suite runs, THE test suite SHALL verify that no evaluation output is read by any runtime process, by running the loop with an evaluation result file present and unreadable under the runtime access rights, and SHALL include a positive control: a test-only runtime configuration that names the evaluation output location must be rejected.
11. IF the access-rights verification of this requirement fails or cannot be completed, THEN THE Loop_Orchestrator SHALL refuse to start a Run, SHALL report an error indicating which check failed, and SHALL create no Run_Volume and no Run directory.
12. THE Run_Manifest SHALL record the result of each isolation check (import analysis, Ground_Truth read denial, mount inspection) as `verified` or `failed`, together with the access rights measured, in fields that are separate from the `payload_audit` field of Requirement 2.14, and SHALL NOT record a check as `verified` unless it was executed in that Run.
13. THE test suite SHALL treat a path-string check, a name-based filter, or a code-level guard as insufficient evidence for criteria 2, 3, and 8, and SHALL NOT count such a check as satisfying them.
14. THE Loop_Orchestrator SHALL verify, in every Run and before the first AI_Provider call or Experiment, that the operating system or container access rights deny read, list, and stat access to the Ground_Truth and to `evaluation/` (the Ground_Truth access-denial verification). THE verification SHALL be mandatory for every Run, including every Run with the Mock_Provider, and no configuration value, flag, or approval SHALL waive it.
15. IF the Ground_Truth access-denial verification has not been executed and passed in a Run, THEN THE Launcher and THE Loop_Orchestrator SHALL NOT start the Run, and THE Run_Manifest of any Run SHALL record the result of this verification in the field `ground_truth_access_denial`.
16. THE test suite SHALL test the Ground_Truth access-denial verification separately from the Payload_Audit (Requirement 2.14), and neither result SHALL be counted as evidence for the other; a Run requires both to pass.

### Requirement 16: Real AI Execution Environment (Kiro_CLI_Provider)

**User Story:** As a Phoenix engineer, I want the real AI to run in an environment that cannot reach the repository or the legacy system, so that the safety of the AI call is established by environment rights and not by trust.

#### Acceptance Criteria

1. THE Kiro_CLI_Provider SHALL execute Kiro CLI only inside the AI_Sandbox, a dedicated container that no other Phoenix component uses.
2. THE AI_Sandbox SHALL NOT mount the repository, the Docker socket, or any existing user HOME directory; the only mounts permitted SHALL be the per-call input location and the AI_Sandbox's own empty HOME and working directories, and the list of actual mounts SHALL be recorded in the verification record.
3. WHEN the Kiro_CLI_Provider starts a call, THE AI_Sandbox SHALL provide an empty HOME directory and an empty working directory, and SHALL contain no file other than the per-call input and the Kiro CLI installation itself.
4. THE AI_Sandbox SHALL contain zero `.kiro` steering files, spec files, hook files, and MCP configuration files visible to the Kiro CLI process.
5. THE AI_Sandbox SHALL have Kiro CLI knowledge and code-intelligence features disabled, and the verification record SHALL state the observed state of each feature.
6. THE Kiro_CLI_Provider SHALL configure Kiro CLI with zero tools and zero MCP servers as the target state, and SHALL NOT depend on the name of any Kiro CLI flag or setting that has not been verified on the real Kiro CLI.
7. IF the output of a Kiro CLI call contains at least 1 tool-call event, THEN THE Kiro_CLI_Provider SHALL fail the call, discard the AI response of that call, record the event, and return an error to the Loop_Orchestrator.
8. IF the Kiro_CLI_Provider cannot determine whether the output contains a tool-call event, THEN THE Kiro_CLI_Provider SHALL treat the call as failed.
9. THE Kiro_CLI_Provider SHALL apply a per-call time limit equal to the per-call limit of Requirement 11.10 (default 120 seconds).
10. IF a Kiro CLI call exceeds the per-call time limit, THEN THE Kiro_CLI_Provider SHALL kill the Kiro CLI process and all of its child processes, fail the call, and record the timeout; THE Loop_Orchestrator SHALL then apply the retry limit of Requirement 11.
11. THE AI_Sandbox SHALL run as a non-root user, SHALL have configured CPU and memory limits, and SHALL publish no port.
12. THE AI_Sandbox SHALL NOT join the `legacy-internal` or `legacy-api` networks, so that the AI has no network route to the Legacy_App.
13. WHILE tool disabling and MCP disabling have not been verified on the real Kiro CLI, THE Run_Manifest SHALL record the safety status of the Kiro_CLI_Provider as `UNVERIFIED`.
14. THE Kiro_CLI_Provider SHALL NOT change the safety status from `UNVERIFIED` to verified unless a verification record exists that was produced on the real Kiro CLI and that shows zero tools and zero MCP servers available to the AI.
15. THE verification record of the AI_Sandbox SHALL state the access rights that were measured (mounts, visible files, environment variables by name, network routes) and SHALL NOT assume any right that was not measured.
16. IF the safety status is `UNVERIFIED` or the verification record is missing, THEN THE Loop_Orchestrator SHALL refuse to transmit the synthetic source to a third-party AI service unless a human has given the explicit approval of Requirement 21.11 for that Run.
### Requirement 17: AI Output as Untrusted Input

**User Story:** As a Phoenix engineer, I want all AI output treated as untrusted, so that a faulty or hostile response cannot cause harm.

#### Acceptance Criteria

1. THE Loop_Orchestrator SHALL treat every AI_Provider response as untrusted input and SHALL NOT use any part of a response until it has passed the size and count checks of criterion 2, the parsing of criterion 5, and the schema validation of Requirements 4 and 7.
2. THE Loop_Orchestrator SHALL enforce configurable limits on each AI_Provider response, with the following defaults: maximum response size 262,144 bytes (256 KiB), maximum 50 Claims per Hypothesis, maximum 5 Citations per Claim, maximum 10 Experiments per response, maximum 10 requests per Experiment, and maximum 8,192 bytes per request body. A limit value SHALL be an integer of at least 1.
3. IF a response exceeds the size limit, THEN THE Loop_Orchestrator SHALL reject the whole response without parsing it, record the rejection reason and the limit that was exceeded in the Evidence_Store, and use no part of the response.
4. IF a parsed response exceeds a count limit, THEN THE Loop_Orchestrator SHALL reject the whole response, record the rejection reason and the limit that was exceeded in the Evidence_Store, and use no part of the response.
5. WHEN a response is within all limits, THE Loop_Orchestrator SHALL parse it only as JSON and validate it against the schemas of Requirements 4 and 7.
6. IF a response is not valid JSON, is nested deeper than 32 levels, contains duplicate keys in one object, or contains a field not defined by the applicable schema, THEN THE Loop_Orchestrator SHALL reject the whole response, record the rejection reason, and use no part of the response.
7. THE Loop_Orchestrator SHALL NOT execute, evaluate, or interpret AI output as code, shell command, file path, URL, or template, other than evaluating Rule_Expression_Language expressions with the evaluator of Requirement 4.6. THE Experiment_Runner SHALL take Test_API paths and methods only from requests that passed the Experiment_Policy of Requirement 8.
8. WHEN AI output is stored or displayed, THE Evidence_Store SHALL store it as unmodified data (the exact received bytes plus their SHA-256 hash), and any display of it SHALL escape it as plain text and SHALL NOT render it as markup or execute it as script.
9. IF a response is rejected under criterion 3, 4, or 6, THEN THE Loop_Orchestrator SHALL count the rejection as one failed AI_Provider call under the retry limit of Requirement 11, and SHALL NOT pass any text of the rejected response to any later AI_Provider request.
10. THE test suite SHALL verify criteria 3, 4, 6, and 7 using Mock_Provider responses that are oversized, over-count, malformed, duplicate-key, deeply nested, contain an undefined field, and contain a command string, a path traversal string, and markup in text fields, and SHALL verify that each such response is rejected or stored as inert data with no side effect on the Legacy_App, the file system, or the process environment.

### Requirement 18: Network Isolation and Residual Risks

**User Story:** As a Phoenix engineer, I want the network boundaries kept explicit, so that unverified paths are never assumed blocked.

#### Acceptance Criteria

1. THE AI_Discovery_Loop SHALL operate only on the synthetic Legacy_App and on the synthetic data of legacy-sample.
2. THE Experiment_Runner SHALL reach the Legacy_App only through the loopback-published Reverse_Proxy address or the configured internal Test_API address, and SHALL NOT publish any new port.
3. ### Requirement 23: Human Approval Records

**User Story:** As a project owner, I want human approvals recorded in a store that no AI can write or change, so that approval status is always the result of a real human decision.

#### Acceptance Criteria

1. THE Approval_Store SHALL hold Approval_Records outside every Run directory (for example under `discovery/approvals/`). Each Approval_Record SHALL contain these fields, all mandatory except `supersedes` (criterion 12):
   - the approver identity, a non-empty string of 1 to 100 characters;
   - a timestamp in ISO 8601 with offset;
   - a target, which is a Claim revision identifier together with its Run identifier, a Run identifier, or a Gate identifier;
   - a decision (`approved`, `rejected`, or `needs_changes`);
   - a rationale of 1 to 2000 characters that contains at least one non-whitespace character;
   - `recorded_by`.
2. THE Approval_Store SHALL be append-only and hash-chained. Each Approval_Record SHALL carry a sequence number and the SHA-256 hash of the immediately preceding record. Sequence numbers SHALL start at 1 and increase by exactly 1 with no gaps. The first record SHALL carry the genesis value of 64 zero characters. THE Approval_Store SHALL reject any request to modify or delete a stored record, leave every stored record byte-identical, and append a record of the rejection.
3. THE runtime container SHALL have no write access to the Approval_Store (read-only mount or no mount). THE test suite SHALL verify the absence of write access under the runtime access rights, with a positive control that the host-side command can write.
4. THE AI output schemas of Requirements 4 and 7 SHALL contain no approval field. No AI SHALL create, change, or delete an Approval_Record. This covers the runtime AI, the AI_Provider, and the Kiro development agent acting on its own initiative.
5. THE Approval_Store SHALL accept Approval_Records only from a host-side human command. The command SHALL require the caller to supply the approver, decision, target, rationale, and an actor declaration (`human` or `kiro-development-agent`) explicitly, and it SHALL apply no default for any of them. THE Approval_Store SHALL set the timestamp from the host clock in ISO 8601 with offset and SHALL NOT accept a caller-supplied timestamp. THE Approval_Store SHALL set `recorded_by` to the declared actor. IF the actor declaration is missing or has any other value, THEN THE Approval_Store SHALL reject the request under criterion 7.
6. IF AI output contains approval-like content (for example a field, status, or text that claims a human approval), THEN THE Loop_Orchestrator SHALL ignore that content and SHALL NOT create an Approval_Record. It SHALL also record in the Evidence_Store that approval-like content was discarded, without the discarded value (Requirement 6.16).
7. IF an Approval_Record to be stored meets any of the following conditions, THEN THE Approval_Store SHALL reject the record, leave the Approval_Store byte-identical, report the name of each missing or invalid field, and cause the host-side command to exit with a non-zero status:
   - it lacks the approver identity, the timestamp, the target, the decision, the rationale, or `recorded_by`;
   - a field violates the limits of criterion 1;
   - its decision is outside `approved`, `rejected`, and `needs_changes`;
   - its timestamp is not ISO 8601 with offset;
   - its target cannot be resolved to an existing Claim revision of an existing Run, to an existing Run, or to a Gate identifier defined in Requirement 21.
8. THE Kiro development agent SHALL NOT create an Approval_Record on its own initiative. THE Kiro development agent MAY run the host-side command only with approver, decision, target, and rationale values that the human stated explicitly in the conversation. It SHALL NOT infer, default, complete, or paraphrase any of those values. It SHALL NOT treat the approval of a spec document, a design document, or a task list as the human's statement of any other approval. In that case, `recorded_by` SHALL be `kiro-development-agent`.
9. WHEN the verification operation is invoked on the Approval_Store, THE Approval_Store SHALL recompute every hash-chain link and modify no file. It SHALL report each mismatch with the record sequence number and the kind (`modified`, `missing`, or `chain_break`). It SHALL exit with status 0 if no mismatch exists, and with a non-zero status otherwise.
10. THE approvals inside `evaluation/` (Ground_Truth and Migration_Decisions) SHALL remain out of scope of this requirement and SHALL NOT be changed, read into, or duplicated by the Approval_Store.
11. FOR ALL valid Approval_Records, serializing, storing, loading, and parsing SHALL produce a record equal to the original (round-trip property).
12. WHEN a human states that an earlier Approval_Record is to be corrected or withdrawn, THE host-side command SHALL accept only a new Approval_Record with a mandatory `supersedes` field. This field holds the sequence number of one earlier record with the same target. The new record SHALL contain all fields of criterion 1 and SHALL pass criterion 7. THE Approval_Store SHALL keep the superseded record unchanged, readable, and in the chain. IF `supersedes` names a non-existent sequence number, a record with a different target, or a record that is already superseded, THEN THE Approval_Store SHALL reject the new record under criterion 7. The Approval status of the target SHALL be derived as defined in Requirement 6.9, and a superseding record SHALL be the latest record for its target at the time it is stored.
13. IF writing an Approval_Record fails, or two invocations of the host-side command run at the same time, THEN THE Approval_Store SHALL leave no partially written record visible to the verification operation. It SHALL store each concurrently accepted record with a distinct sequence number and a valid hash link. On a failed write it SHALL report an error and exit with a non-zero status. A record that fails to write SHALL NOT be reported as stored.
14. WHEN the verification operation runs on the Approval_Store without an external anchor (a last sequence number and last-record hash held outside the Approval_Store), THE Approval_Store SHALL report only that no mismatch exists among the records present, and SHALL NOT report that the store is complete or that removal of trailing records was excluded. WHERE an external anchor is supplied, THE Approval_Store SHALL report a mismatch of the kind `missing` if the anchored record is absent and of the kind `modified` if its hash differs.

9. IF the runtime container is started without a Run_Lease, or with a Run_Lease that is missing, malformed, bound to a different Run identifier, revoked, or invalid, THEN THE runtime SHALL refuse to start the Run, SHALL exit with a non-zero status, SHALL send no request to the Legacy_App, and SHALL write no Experiment record.
10. A Windows named mutex is released by the operating system when the process that owns it exits, whether the process ends normally, with an error, or is killed. THE Launcher SHALL therefore own both locks in its own process and SHALL NOT delegate them to a child process or to the runtime container.
11. WHEN the Run ends normally or ends with an error, THE Launcher SHALL stop the runtime container, SHALL confirm that the container is no longer running, SHALL revoke the Run_Lease, and only then SHALL release the mutex, and SHALL release the Run-level lock after the export under criterion 6, so that no state exists in which a lock is released while the runtime container is still running.
12. IF the Launcher process is killed, THEN THE operating system SHALL release the named mutex, THE Run_Lease SHALL become invalid, and any runtime container that is still running SHALL stop within 10 seconds (the runtime SHALL detect the invalid Run_Lease, send no further request to the Legacy_App, and exit; and a subsequent Launcher start or recovery step SHALL, after it has acquired both locks and before it creates a new Run directory, stop any runtime container left running from a previous Run (identified by its container label), so that a live Run owned by another Launcher is never stopped). THE Run_Manifest of the interrupted Run, if written to the Run_Volume, SHALL record the termination reason `launcher_killed`; IF it cannot be written, THEN THE next Launcher start SHALL mark the Run as `interrupted` by writing a Reason_File into the Incoming_Export of that Run (creating `discovery/runs/.incoming/<run-id>/` if it does not exist) and SHALL keep the Run_Volume for diagnosis. The `interrupted` marking applies to the Run_Volume and the export, and a Run marked `interrupted` SHALL have no Completion_Marker.
13. THE test suite SHALL show, with automated tests that run without an external AI service, all of the following:
   - (a) WHILE a Run holds the Run_Lock, the existing conformance runner, started without modification, exits with status 2 and runs no scenario;
   - (b) WHILE the conformance runner holds the mutex, the Launcher exits with a non-zero status, reports `conformance_mutex`, creates no Run directory, and starts no runtime container;
   - (c) WHILE one Run holds the Run_Lock, a second Launcher start exits with a non-zero status, reports `run_lock`, creates no Run directory, and starts no runtime container;
   - (d) after a normal end, after an error end, and after the Launcher process is killed, the mutex and the Run-level lock can each be acquired by a new process within 10 seconds after the Launcher process has exited or been killed (an acquisition of the mutex in the abandoned state counts as acquired and is handled under criterion 17), the runtime container is not running, and the Run_Lease is rejected by the runtime; and, WHEN the mutex is acquired in the abandoned state, the Launcher starts no Experiment and no runtime container, releases the mutex, reports `conformance_mutex_abandoned`, exits with a non-zero status, and a following explicit start performs the leftover-container stop and the `interrupted` marking of criterion 12, while the existing conformance runner, started without modification against an abandoned mutex, runs no scenario (exit status 2 or an error exit);
   - (e) in each case of (d), the container-stop confirmation precedes the lock release in the normal-end and error-end cases, and in the kill case no runtime container is running 10 seconds after the kill.
14. THE test suite SHALL use the real Windows named mutex and not a mock for criterion 13(a) to 13(d).
15. IF the runtime detects that the Run_Lease became invalid while a Run is in progress, THEN THE runtime SHALL not start the next Experiment, SHALL record the remaining Experiments as `not_executed` with the reason `lease_unavailable` (Requirement 9.5), SHALL stop the Run with termination reason `lease_unavailable`, and SHALL exit with a non-zero status.
16. THE mutual exclusion of this requirement SHALL be guaranteed for a single host and a single Windows logon session only, because the `Local\` named mutex namespace is per logon session. THE project documentation SHALL state that exclusion across logon sessions, users, or hosts is NOT guaranteed.
17. IF the Launcher acquires the mutex of criterion 4 in the abandoned state (the previous owner exited without releasing it), THEN THE Launcher SHALL start no Experiment and no runtime container for that start attempt, SHALL create no Run_Volume, SHALL release the mutex and any Run-level lock it holds, SHALL report `conformance_mutex_abandoned`, SHALL exit with a non-zero status, and SHALL leave the recovery of the affected Run to the next explicit start, which first performs the leftover-container stop and the `interrupted` marking of criterion 12.
18. IF the existing Ground_Truth conformance runner acquires or meets the mutex in the abandoned state, THEN the acceptance condition SHALL be that the conformance runner runs no scenario, and it MAY exit with status 2 or with an error.
19. THE project documentation, the Run_Manifest, and the open items SHALL list the single-session scope of criterion 16 as a residual risk with status `unresolved`.
