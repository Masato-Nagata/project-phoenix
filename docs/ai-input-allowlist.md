# AI Input Allowlist Policy

Status: accepted (legacy-sample, Phase 2 follow-up; machine-readable form and reference checks added in Phase 4)

## Purpose

The Phoenix runtime AI (spec-restorer, modernizer, and any future analyzer-driven call) must infer business rules from the legacy source alone. Anything that states or implies the correct answer must never reach it. This document defines what the AI may receive and how that is enforced.

## Policy: allowlist, deny by default

AI input is defined by an explicit list of concrete file paths. Anything not on the list is excluded. A file is never added because it exists in an allowed directory, and the list is never generated by enumerating directories or expanding wildcards at run time. A new file is excluded simply by not being on the allowlist.

### Allowed (legacy-sample)

| File | Reason |
|------|--------|
| `legacy/src/index.php` | Application source; the analysis target |
| `legacy/src/db.php` | Application source |
| `legacy/src/products.php` | Application source |
| `legacy/src/orders.php` | Application source |
| `legacy/src/utils.php` | Application source |
| `legacy/sql/schema.sql` | Table definitions |
| `legacy/sql/seed.sql` | Initial data |

The machine-readable form of this table is `docs/ai-input-allowlist.json` (interim location; the analyzer spec decides the final one). Both must list the same files in the same order; `tests/legacy-sample/test_ground_truth_schema.ps1` (GS29) fails if they differ.

Adding any file, including a new PHP file under `legacy/src/` or a config file such as `legacy/src/.htaccess` or `legacy/Dockerfile`, requires an explicit change to this table and to `docs/ai-input-allowlist.json` in a reviewed commit.

### Not allowed

`tests/`, `evaluation/`, `.kiro/`, `docs/`, `infra/`, `.env*`, every `README.md` (including `legacy/README.md`), `.git/`, and anything else not in the allowed table.

## Rules for analyzer and any AI-bound component

1. Take the allowlist as explicit input. Do not discover input by scanning or recursively walking `legacy/`, the repository root, or any other directory, and do not expand wildcards to add files.
2. Resolve each path to a real path and verify it is inside an allowed pattern. Reject `..` traversal and symlinks that leave the allowed set.
3. Fail closed: an unreadable or non-matching path stops the run; it is never skipped silently.
4. Write an input manifest (path and content hash per file) for every run so the exact AI input can be audited. The manifest must equal the allowlist exactly; an extra or missing file is a failure.
5. Treat comments as content. Files on the allowlist must not contain comments that explain business rules (requirement 10.3).

## Verification

| Check | When | Status |
|-------|------|--------|
| Rule check with a reference builder: exactly the listed files, manifest with hashes, fail closed on traversal, absolute paths, wildcards, directories, nested or non-source files, duplicates, missing files, and junctions | `tests/legacy-sample/test_ai_input_isolation.ps1` (`lib/ai-input-builder.ps1`) | implemented (Phase 4) |
| Canary decoys in `evaluation/`, `tests/`, `docs/`, `.kiro/`, READMEs, `.env` and next to allowed files never reach the bundle; a naive directory scan does (negative control); the Ground Truth canary exists only in `ground-truth.json` | `test_ai_input_isolation.ps1` | implemented (Phase 4) |
| Manifest contains only allowlisted paths | Every analyzer run; analyzer unit test | not implemented (analyzer does not exist yet) |
| Outbound payload scan: the text actually sent to `ai-client` contains no canary string from `evaluation/ground-truth/` and no path outside the allowlist | spec-restorer tests | **unverified** (spec-restorer and ai-client do not exist yet) |
| `docker-compose.yml` has no `evaluation` mount, and running containers show no such mount | `test_ground_truth_isolation.ps1`; rerun before release | implemented |
| Allowlisted files have no business-rule comments | Review checklist; grep for comment lines in `legacy/src` and `legacy/sql` | checked in task 4.5 |

A path log alone is not sufficient evidence. The payload scan on what is really sent is the authoritative check. The reference builder shows that the rule works; it does not show that the future analyzer follows it.

## Scope note: development agent vs runtime AI

The Kiro IDE development agent that writes this repository is a different actor from the Phoenix runtime AI. The development agent may read tests and ground-truth files while building and reviewing. This policy governs only the Phoenix runtime AI.

## Test placement

Tests for legacy-sample live in `tests/legacy-sample/`, outside `legacy/`, because expected values in tests restate the business rules. Phase 3 and Phase 4 tests follow the same location.
